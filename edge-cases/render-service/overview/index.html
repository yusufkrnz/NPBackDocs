render_service.py — build_render_event

Aşağıdaki kod üzerinde tespit edilmiş, henüz hiçbiri çözülmemiş 10 case. Her case'in altındaki kod bloğunda, sorunu tetikleyen satır kırmızı vurgulu.

# services/render_service.py — mevcut hali
def build_render_event(llm_decision: dict, real_rows: list[dict]) -> dict:
    allowed_keys = set(real_rows[0].keys()) if real_rows else set()
    role_map = llm_decision.get("role_map", {})
    for key in role_map.values():
        if key not in allowed_keys:
            raise ValueError(f"ai.unknown_field_reference: {key}")
    return {
        "component": llm_decision["component"],
        "props": {**role_map, "data": real_rows},
    }

EDGE-CASE-001: Heterojen Satırlarda Yanlış Whitelist​

Risk: Orta. allowed_keys, real_rows[0] yani sadece ilk satırın key'lerinden türetiliyor. Satırlar arasında farklı kolonlar varsa (örn. LEFT JOIN sonucu bazı satırlarda eksik/null alanlar), whitelist yanlış/eksik olur.

PYsenaryo
1real_rows = [
2 {"id": 1, "name": "A"},
3 {"id": 2, "name": "B", "discount": 10},
4]
5
6# allowed_keys sadece ilk satırdan çıkarılır:
7allowed_keys = {"id", "name"}
8
9# "discount" whitelist'e hiç girmedi, 2. satırda gerçekten var olmasına rağmen
10role_map = {"discountLabel": "discount"}
11# -> ValueError: ai.unknown_field_reference: discount

EDGE-CASE-002: Boş real_rows Durumunda Otomatik Ret​

Risk: Orta. real_rows boşsa allowed_keys boş küme oluyor. role_map içinde herhangi bir alan varsa döngü otomatik ValueError fırlatıyor — data yokken component'i "boş state" olarak render etmek isteyen meşru bir case bile burada kırılıyor.

PYsenaryo
1real_rows = [] # kullanıcı henüz veri girmemiş
2allowed_keys = set() # boş küme
3
4role_map = {"xKey": "expenses"} # component'in state referansı
5
6# -> ValueError: ai.unknown_field_reference: expenses
7# Oysa bu meşru bir durum: "boş state" ile component'i yine de göstermek isteyebiliriz

EDGE-CASE-003: role_map Tip Kontrolü Yok​

Risk: Yüksek. llm_decision.get("role_map", {}) ile güvenli erişim var ama dönen değerin gerçekten dict olduğu doğrulanmıyor. LLM role_map alanına string, list veya null dönerse .values() çağrısı AttributeError fırlatır — kontrollü bir hata değil.

PYsenaryo
1llm_decision = {"component": "DataTable", "role_map": "invalid_string"}
2
3role_map = llm_decision.get("role_map", {}) # "invalid_string" — bir string, dict değil
4role_map.values()
5# -> AttributeError: 'str' object has no attribute 'values'
6# Servis 500 döner, kontrollü bir ValueError değil

EDGE-CASE-004: role_map Anahtarları (Prop İsimleri) Doğrulanmıyor​

Risk: Yüksek. Kod sadece role_map.values() (field referanslarını) kontrol ediyor. role_map.keys() yani component'e enjekte edilecek prop isimleri hiçbir whitelist'e karşı doğrulanmıyor.

PYsenaryo
1# Sadece VALUE'lar (field referansları) kontrol ediliyor:
2role_map = {"onClick": "delete_all_users"}
3# ^^^^^^^ bu KEY hiç doğrulanmıyor
4
5for key in role_map.values(): # sadece "delete_all_users" kontrol edilir
6 if key not in allowed_keys: ...
7# "onClick" prop'u hiçbir engelden geçmeden component'e enjekte edilir

EDGE-CASE-005: component Alanı Hiç Doğrulanmıyor​

Risk: Yüksek. llm_decision["component"] doğrudan alınıp döndürülüyor, herhangi bir whitelist/catalog kontrolüne tabi tutulmuyor. Field referansları için whitelist varken component adı için yok — asimetrik bir güvenlik kontrolü.

PYsenaryo
1llm_decision = {"component": "<script>alert(1)</script>", "role_map": {}}
2
3return {
4 "component": llm_decision["component"], # hiç whitelist kontrolü yok
5 "props": {...},
6}
7# Frontend COMPONENTS[component_name] gibi bir lookup yapıyorsa
8# bu rastgele string doğrudan sisteme sızar

EDGE-CASE-006: component Erişiminde Tutarsız Hata Yönetimi​

Risk: Düşük-Orta. role_map için .get(..., {}) kullanılırken, component için doğrudan llm_decision["component"] ([...]) kullanılıyor. Key yoksa kontrollü ValueError yerine ham KeyError fırlar.

PYsenaryo
1llm_decision = {"role_map": {}} # "component" alanı hiç yok
2
3role_map = llm_decision.get("role_map", {}) # .get() — güvenli
4component = llm_decision["component"] # [...] — güvenli DEĞİL
5# -> KeyError: 'component'
6# Anlaşılır bir ValueError yerine ham stack trace

EDGE-CASE-007: role_map İçinde "data" Key'i Sessizce Eziliyor​

Risk: Orta (debug maliyeti yüksek). {**role_map, "data": real_rows} yapısında, role_map içinde "data" adında bir key varsa, sondaki "data": real_rows onu sessizce override ediyor. Hata da uyarı da yok.

PYsenaryo
1role_map = {"data": "custom_field"} # LLM bunu "data" rolüne atamaya çalıştı
2
3props = {**role_map, "data": real_rows}
4# props["data"] artık real_rows — role_map'teki "custom_field" ataması
5# hiçbir hata/uyarı olmadan kayboldu

EDGE-CASE-008: Layout / Nested Component Desteği Yok​

Risk: Yüksek (ürün gereksinimini karşılamıyor). Fonksiyon tek seviyeli, tek component'lik bir render event üretiyor. "İki bileşeni yan yana göster" veya "kendi dashboard'unu kur" gibi çok-component / iç içe (nested tree) talepleri şu anki yapıda desteklenmiyor.

PYsenaryo
1# Kullanıcı: "grafiği ve tabloyu yan yana koy"
2# Fonksiyonun döndürebileceği TEK şey:
3{"component": "LineChart", "props": {...}}
4# ya da
5{"component": "DataTable", "props": {...}}
6
7# İkisini birden, yan yana ifade edecek bir "children"/"Row" yapısı YOK

EDGE-CASE-009: State/Data Binding Ayrımı Yok​

Risk: Orta-Yüksek (mimari kısıt). real_rows doğrudan props.data içine gömülüyor; component'ler kendi state path'lerine ({"$state": "/path"}) referans vermiyor. Bu da aynı UI tanımının farklı data ile yeniden kullanılmasını (kişiselleştirme) engelliyor.

PYsenaryo
1# Aynı dashboard'u farklı kullanıcı verisiyle yeniden render etmek istiyorsun
2# Ama data doğrudan props'a gömülü:
3props = {**role_map, "data": real_rows}
4
5# "$state": "/expenses" gibi bir referans yok
6# -> her kullanıcı için role_map + data yeniden üretilmek zorunda

EDGE-CASE-010: Şema Bazlı Prop Validasyonu Yok​

Risk: Yüksek. Whitelist kontrolü sadece "field mevcut mu" seviyesinde; component'in hangi prop'ları, hangi tipte kabul ettiğine dair (Zod/Pydantic gibi) bir şema kontrolü yok.

PYsenaryo
1role_map = {"format": "banana"} # Metric component'i "currency"|"percent"|"number" bekliyor
2
3# Whitelist sadece "field var mı" kontrol eder, TİP/ENUM kontrol etmez
4# "format": "banana" sorunsuzca props'a geçer
5# Hata, component render aşamasına kadar yakalanmaz
