# AI Katmanı — Genel Bakış

Üründe bir chat arayüzü var: kullanıcı doğal dille bir şey sorduğunda, LLM ekrana **dinamik bir UI** (tablo, grafik, kart vb.) bastırıyor. Bu sayfa, bunun nasıl güvenli ve öngörülebilir şekilde yapıldığını anlatıyor.

## Çözülen tehdit

İlk akla gelen yaklaşım — tüm endpoint'leri, DB şemasını LLM'in prompt'una vermek ve "uygun gördüğünü çağır" demek — ciddi bir güvenlik açığıdır:

- **Prompt injection**: Kullanıcı mesajı içine gizlenmiş bir talimat, LLM'i yetkisi olmayan bir endpoint'i çağırmaya ikna edebilir
- **Veri sızıntısı**: LLM'e "her şeyi" vermek, LLM'in normalde erişmemesi gereken alanları da görmesi anlamına gelir
- **Doğrulanamaz çıktı**: LLM'in serbest metin (HTML) üretmesi, o metnin güvenle parse edilebileceği garantisini vermez (XSS, şema garantisi yok)

## Çözüm: guardrailed generative UI

Bu mimarinin endüstri karşılığı **"guardrailed generative UI"** — LLM arayüzü doğal dilden üretir ama sadece senin tanımladığın bir kataloğun sınırları içinde. Prensip:

> LLM hiçbir zaman gerçek endpoint URL'ini, DB bağlantısını, secret'ı ya da gerçek veri değerini görmez — sadece "bu isimde bir şey var, şu şekli/tipi alır" bilgisini görür.

Bu son madde kritik ve sıkça kaçırılıyor: LLM'e "veriyi getir" dedirtip dönen sonucu (gerçek müşteri adı, tutar, sipariş no gibi) tekrar LLM'e verip "şimdi bunu göster" dedirtmek — LLM'in konuşma geçmişine gerçek, potansiyel hassas veri sokmak demektir. Bunun yerine LLM'e sonucun sadece **şekli** (kaç satır, hangi kolonlar, hangi tip) verilir; LLM hangi component'i seçeceğine bu şekle bakarak karar verir. Gerçek satır verisi, LLM'in kararından **sonra**, backend tarafından client'a giden JSON'a eklenir — LLM bu veriyi hiç görmez, üretmez. Detay için bkz. [Neden LLM'e Ham Veri/Endpoint Vermiyoruz](/ai/why-no-raw-data).

### Peki veri gerçekte nasıl ekrana basılıyor

En sık sorulan soru bu: LLM veriyi hiç görmüyorsa, tabloyu dolduran gerçek satırlar nereden geliyor? Cevap: LLM'in kararı ile gerçek veri, LLM'in hiç haberi olmadan backend'de **birleştiriliyor** (merge):

<CodeRail>
  <CodeEditor
    filename="services/render_service.py"
    code={`def build_render_event(llm_decision: dict, real_rows: list[dict]) -> dict:
    # llm_decision = {"component": "DataTable", "columns": ["Müşteri", "Tutar"]}
    # LLM'in kararında "rows" hiç yok — şema buna izin vermiyor (bkz. JSON Schema)
    component = llm_decision["component"]
    columns = llm_decision["columns"]

    # Gerçek satırlar burada ekleniyor — LLM'in kararından SONRA, backend tarafından
    return {
        "component": component,
        "props": {
            "columns": columns,
            "rows": real_rows,
        },
    }`}
  />
</CodeRail>

Bu fonksiyonun çağrıldığı yer, akışın tamamını özetler:

<CodeRail>
  <CodeEditor
    filename="routers/chat.py"
    code={`# 1) Gerçek veri, LLM'e hiç gitmeden, doğrudan DB'den çekilir
tool_result = await run_tool(tool_call.name, tool_call.input)

# 2) LLM'e sadece ŞEKİL gönderilir (satır sayısı, kolon adları/tipleri) — bkz. Akış
llm_decision = await ask_llm_to_choose_component(shape_of(tool_result))

# 3) Gerçek veri + LLM'in kararı burada birleştirilir — LLM bu adımı hiç görmez
render_event = build_render_event(llm_decision, real_rows=tool_result["rows"])

await send_to_client(render_event)`}
  />
</CodeRail>

`real_rows`, adım 1'de zaten backend'in elinde — LLM'e hiç gönderilmedi, sadece bekletildi. LLM'in tek katkısı `component` ve `columns` seçmek; `rows`'u LLM ne üretiyor ne de görüyor.

## Neden HTML değil JSON

LLM'e ham HTML/React kodu yazdırmak yerine, LLM'den yapılandırılmış JSON isteniyor: `{"component": "DataTable", "params": {...}}`. Bunun nedeni HTML'in "parse edilmesi gereken, şema garantisi olmayan serbest metin" olması — JSON ise native tool/function calling ile model sağlayıcı (Anthropic/OpenAI) tarafından zaten şemaya karşı doğrulanıyor. Detay için bkz. [Referanslar](/ai/references).
